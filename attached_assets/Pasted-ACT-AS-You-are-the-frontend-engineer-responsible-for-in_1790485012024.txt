--------------------------------------------------
ENDPOINT
--------------------------------------------------

The backend exposes one HTTP Cloud Function:

manual-reconciliation-api

The deployed function URL must be supplied to the frontend through frontend
configuration/environment variables.

DO NOT hard-code a guessed Cloud Function URL.

Use the frontend repository's existing environment-variable convention.

For a Vite application, this will generally require a VITE_-prefixed variable

If no suitable variable exists, add one and document it.

Conceptually:

VITE_MANUAL_RECONCILIATION_API_URL

This name is an example unless an existing naming convention makes another

--------------------------------------------------
AUTHENTICATION
--------------------------------------------------

Obtain a current Firebase ID token from the currently authenticated Firebase
user.

Send:

Authorization: Bearer <Firebase ID token>

Also send:

Content-Type: application/json

DO NOT use:

X-Firebase-ID-Token

DO NOT send user_id as reconciliation identity.

The backend verifies the Firebase ID token using Firebase Admin and derives the
authoritative acting user ID from the verified token.

--------------------------------------------------
MANUAL MATCH
--------------------------------------------------

HTTP:

POST <manual-reconciliation-function-url>

Headers:

Authorization: Bearer <Firebase ID token>
Content-Type: application/json

Body:

{
  "action": "match",
  "forecast_id": "FORECAST_DOCUMENT_ID",
  "transaction_id": "TRANSACTION_DOCUMENT_ID"
}

Successful response has the following general shape:

{
  "ok": true,
  "status": "matched",
  "forecast_id": "FORECAST_DOCUMENT_ID",
  "transaction_id": "TRANSACTION_DOCUMENT_ID",
  "match_source": "manual",
  "replaced_transaction_id": null,
  "claim_released": false,
  "learning_recorded": true
}

Some response values vary depending on whether an existing relationship was
replaced.

--------------------------------------------------
REPLACEMENT / REMATCH
--------------------------------------------------

IMPORTANT:

The same match endpoint performs atomic replacement.

Example:

Current state:

Forecast F -> Transaction A

User drops Transaction B onto Forecast F.

DO NOT do:

unmatch(F)
then
match(F, B)

Instead make ONE request:

{
  "action": "match",
  "forecast_id": "F",
  "transaction_id": "B"
}

The backend atomically handles:

- validating F and B
- rejecting conflicting transaction claims
- releasing A when safe
- claiming B
- changing F -> B
- correcting/rejecting the old learned relationship
- confirming the new manual relationship

The frontend must use this single-request replacement behavior.

--------------------------------------------------
MANUAL UNMATCH
--------------------------------------------------

HTTP:

POST <manual-reconciliation-function-url>

Headers:

Authorization: Bearer <Firebase ID token>
Content-Type: application/json

Body:

{
  "action": "unmatch",
  "forecast_id": "FORECAST_DOCUMENT_ID"
}

A normal successful response includes:

{
  "ok": true,
  "status": "unmatched",
  ...
}

If already unmatched, success may contain:

{
  "ok": true,
  "status": "already_unmatched",
  ...
}

Do NOT send transaction_id for unmatch.

The backend determines the currently matched transaction from authoritative
Firestore state.

--------------------------------------------------
ERROR FORMAT
--------------------------------------------------

Backend errors have this shape:

{
  "ok": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable message"
  }
}

Relevant status/error combinations:

400:
- invalid_request
- invalid_action

401:
- unauthenticated

403:
- ownership_denied

404:
- forecast_not_found
- transaction_not_found

409:
- account_mismatch
- transaction_already_claimed
- concurrent_conflict
- invalid_existing_match

405:
- method_not_allowed

503:
- authentication_unavailable

500:
- internal_error

Treat transaction_already_claimed and concurrent_conflict as expected
concurrency outcomes.

They are not application crashes.

Do not automatically overwrite the server result.

Do not blindly retry the conflicting relationship.

Refresh affected reconciliation state.

--------------------------------------------------
CORS
--------------------------------------------------

The backend uses an explicit origin allowlist.

The backend does NOT use:

Access-Control-Allow-Origin: *

The backend environment variable is:

MANUAL_RECONCILIATION_ALLOWED_ORIGINS

The deployed frontend's exact browser origin must be configured there.

If local development produces a CORS error, report the exact frontend origin
that needs to be added to backend configuration.

DO NOT work around CORS by:

- using no-cors fetch mode
- disabling browser security
- creating an insecure proxy
- removing authentication
- falling back to direct Firestore reconciliation writes

--------------------------------------------------
BACKEND-OWNED STATE
--------------------------------------------------

The backend owns these reconciliation fields:

matched_transaction_id
match_source
match_engine_version
match_confidence_score
reconciliation_claimed

The backend also exclusively owns:

- learned aliases

- correction/rejection learning

The frontend may READ appropriate backend-generated fields.

The frontend must NOT directly WRITE them.

==================================================
TASK 8 — PENDING / OPTIMISTIC UI
==================================================

Do not permanently commit a reconciliation relationship in local UI before the
backend accepts it.

A temporary pending visual state is acceptable.

Recommended flow:

1. User initiates match.
2. Mark that specific reconciliation operation pending.
3. Prevent accidental duplicate submission for the same operation.
4. Call backend.
5. Backend succeeds.
6. Allow authoritative Firestore state/listeners to update UI or perform the
   smallest necessary refresh.
7. Clear pending state.

On failure:

1. Clear pending state.
2. Preserve/restore prior relationship display.
3. Show useful error.
4. Refresh authoritative state when appropriate.

Do not globally freeze the whole application for one reconciliation operation.

==================================================
TASK 9 — CONCURRENCY / CLAIM CONFLICTS
==================================================

The backend protects one-to-one transaction ownership.

Example:

Browser displays Transaction T as available.

Before the user finishes dragging T, automatic reconciliation claims:

Forecast A -> Transaction T

User attempts:

Forecast B -> Transaction T

Backend returns:

409 transaction_already_claimed

Expected frontend behavior:

- do not display B -> T as successful
- clear pending state
- show a concise useful message
- refresh affected reconciliation data

Suggested user-facing meaning:

"This transaction was matched while you were making this change. Reconciliation
data has been refreshed."

Exact wording may follow existing product style.

Similarly handle:

409 concurrent_conflict

as stale/concurrent state requiring refresh.

Do not automatically retry either conflict.

==================================================
TASK 10 — ERROR HANDLING
==================================================

Use existing toast/message/error infrastructure where possible.

Map errors appropriately.

401 unauthenticated:

The user's authentication may have expired.

Do not expose raw backend details.

404 forecast_not_found:

Refresh forecast state.

404 transaction_not_found:

Refresh transaction state.

403 ownership_denied:

Do not reveal information about another user's data.

Show a generic inability-to-complete message.

409 account_mismatch:

Tell the user the transaction cannot be matched to that forecast.

409 transaction_already_claimed:

Explain that the transaction has already been matched and refresh state.

409 concurrent_conflict:

Explain that reconciliation state changed and refresh.

409 invalid_existing_match:

Refresh authoritative state and show a generic reconciliation-state error.

503 authentication_unavailable:

Tell the user reconciliation is temporarily unavailable.

500 internal_error:

Show a generic failure.

NETWORK ERROR:

Keep existing relationship state.
Clear pending state.
Allow retry.

Do not show:

- stack traces
- Firebase internals
- raw HTML errors
- sensitive backend details
